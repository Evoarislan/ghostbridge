THE WORK, IN THIS ORDER. Land and gate each part before starting the next.

Part 1: warm Chromium across spawns (design question 1, approved).
Shim startup is about 3 s per spawn (empty script 2.8-3.2 s); it is the
root cause of html-pdf's callPhantom timing failure (suite asserts a
1-2 s conversion; ours takes 4.2-5.9 s) and a contributor to
phantom-html-to-pdf's timeout failures. Keep a Chromium instance warm
across shim spawns so repeat spawns skip the cold launch.
Hard constraints:
- The CLI contract from Sessions 3 and 5 does not move: --version prints
  exactly 2.1.1 exit 0, unknown options fail honestly, exit codes pass
  through, signals forward (128+n), and the console-drain guarantee
  (pending console output delivered before exit) still holds. The gate's
  existing checks prove these; they must stay green unchanged.
- Isolation: a warm instance must never leak page state, cookies, or
  console output between unrelated script runs. If full isolation cannot
  be proven for a shared instance, scope the warm instance to one parent
  process tree and say so in the result file.
- A cold first spawn must behave exactly as today.
- Measure honestly: empty-script wall time and a loadspeed.js run,
  before and after, real numbers in the result file. If callPhantom
  still misses the 1-2 s window after this, report the new numbers and
  the remaining gap; do not tune the suite, the shim's reported timings,
  or anything else to fake the window.

Part 2: per-page header/footer content (design question 2, approved).
html-pdf's suite wants different header content on the first, third, and
last pages. Chromium's printToPDF applies one header template to all
pages. Implement the approved route: when paperSize header/footer
callbacks resolve to different content per page, print each page
separately with its own template and merge the single-page PDFs into
one document.
- The merge dependency is a GhostBridge dependency (a maintained PDF
  library, e.g. pdf-lib), never a member dependency. Record the choice
  and version in the result file.
- Merging must preserve each page's size and MediaBox (the Session 7
  custom.pdf evidence was exactly [0 0 216 504]; that class of check
  must still pass).
- When callbacks resolve to the same content for every page, keep the
  current single-print path.
- Anything still impossible keeps the current behavior: fail loudly
  rather than print wrong output.

Part 3: the webserver module (design question 5, first surface).
Implement PhantomJS's webserver module in gb-runtime's module system:
require('webserver').create(), server.listen(port, handler),
request/response objects with the surface the PhantomJS API documents
and the suites exercise (method, url, headers, post bodies; response
statusCode, headers, write, close, closeGracefully). phantom-workers
starts every worker through require('webserver'), so this unlocks
phantom-html-to-pdf's phantom-server strategy (14 tests).

Part 4: the remaining two surfaces (design question 5), only after
Parts 1-3 are landed and gated.
- page.onInitialized: fire at the PhantomJS-correct point so injectJs
  and waitForJS patterns in phantom-html-to-pdf work.
- Blocking onResourceRequested: requests must be interceptable BEFORE
  they are sent, with networkRequest.abort() and changeUrl(url)
  honored. The current after-the-fact reporting does not satisfy this;
  if the blocking channel cannot be built honestly on the current
  architecture, stop, document exactly where it breaks, and leave the
  surface unimplemented rather than simulate it.
